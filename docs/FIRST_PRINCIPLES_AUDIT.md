# First Principles 監査 — 公理から演繹する機能の過不足

> 作成: 2026-07。手法: First Principles Thinking。
> **既存の [`SURPLUS_AND_GAPS.md`](SURPLUS_AND_GAPS.md) とは分析の向きが逆**。
> あちらは実装から出発する**帰納**(「このコードは到達するか」)。本書は製品定義から
> 出発する**演繹**(「そもそも何が必要か」)。両者を突き合わせることで、
> 「実装されているが不要なもの」と「必要だが存在しないもの」が独立に浮かぶ。
>
> 全ての `file:line` は本文書作成時に grep で実在確認済み。

---

## 0. 出発点: 製品定義を一文に還元する

> **他人のアイドル GPU を、安全に、1 ドル未満で 60 秒借りる。**

この一文から、交渉の余地なく導かれる前提 (公理) を抽出する。「あったら良い機能」
ではなく、**欠けたら製品が論理的に成立しない**ものだけを公理とする。

---

## 1. 公理 (Axioms) — 製品成立の必要条件

| # | 公理 | なぜ交渉不可能か |
|---|------|-----------------|
| **A1** | 借り手と貸し手が**互いを発見**できる | 発見できなければ取引は始まりようがない。ゼロ番目の前提 |
| **A2** | **未知の他人**同士の間に信頼を確立する手段がある | 「他人の GPU」である以上、事前の信頼関係は定義上存在しない |
| **A3** | 借りた GPU で**計算を実際に実行**できる | 実行できなければ提供価値がゼロ。製品の存在理由そのもの |
| **A4** | 実行結果が**正しいと確認**できる | 確認できなければ借り手は払えない (手抜き計算に課金される = free-riding) |
| **A5** | 対価を**移転**する手段がある | 移転できなければ貸し手にインセンティブが無く供給が生まれない |
| **A6** | 機微データの**秘匿を技術的に保証**できる | 「**安全に**」を謳う以上必須。他人のマシンに平文を渡す構造だから |
| **A7** | 途中で**中断しても双方が損しない** | 他人同士の一回限りの取引では、離脱・故障が常態。損する側は二度と参加しない |
| **A9** | **貸し手が借り手から自分を守れる** (2026-08-08 追加) | A1-A7 は全て*借り手*側の要件だった。取引には二者いる。**マシンを壊される・悪用される・法的責任を負わされるなら、対価がいくらでも貸さない** — A5 が参加*動機*を与えるのに対し A9 は参加*条件*を与える。詳細: [`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §4h |

補助公理 (製品成立ではなく採用に必要):

| # | 公理 | 位置づけ |
|---|------|---------|
| **A8** | 使い始めるのに**設定が要らない** | A1-A7 と異なり無くても製品は「動く」。ただし README の 6 約束の一つであり、Rope の差別化軸 |

## 2. 公理 → 必要能力 → 現行実装のマッピング

実装状況: **○** = 実際に機能する / **△** = 型・状態機械はあるが中身が空 / **×** = 存在しない
到達可能性: 4 動詞 (`rope`/`pair`/`run`/`earn`) から実際に呼ばれるか

| 公理 | 必要能力 | 実装 | 到達 | 実体 (file:line) |
|---|---|:--:|:--:|---|
| **A1** | ピア発見 (mDNS/BT/DHT) | △ | ✗ | `pair.rs:615` `record_discovery` は状態機械のみ。`mdns_enabled`/`mdns_service` (`pair.rs:229,231`) は設定値だけで、ソケットを開くコードが存在しない |
| **A2** | 信頼確立 (未知ピアの検証) | △ | ✗ | `trust_store` (`pair.rs:45`) は TOFU のみ。`CapabilityChallenge` (`pair.rs:394`) + `issue_pow_challenge` (`pair.rs:1028`) / `verify_capability_proof` (`pair.rs:1061`) は実装・テスト済みだが CLI 未結線 |
| **A3** | **推論の実行** | **×** | ✗ | **推論エンジンへのバインディングが一行も存在しない**。`llama` の grep ヒットは全てモデル名の文字列 (`first_run.rs:186` の設定値、`intent.rs:1182,1288` のテストデータ) のみ |
| **A4** | 実行の正しさの検証 | △ | ✗ | `VerificationLevel` (`intent.rs:364`) は enum のみ。`proof_satisfies` (`ecash.rs:778`) はコミットメントのハッシュ一致を見るだけで、計算が実際に行われた証明にはならない |
| **A5** | 対価の移転 | △ | ✗ | `mint_tokens`/`spend_proofs`/`open_escrow`/`open_stream` (`ecash.rs:490,523,642,935`) は全て実装・テスト済みだが、**どの動詞からも呼ばれない** (`load_ecash` の読込だけが到達)。加えて BDHKE 署名自体がプレースホルダ |
| **A6** | 秘匿の技術的保証 | △ | ✗ | `perform_attestation` (`confidential.rs:460`) は動くが、`build_evidence_signature` (`confidential.rs:701`) が `unverified-digest:` prefix 付きの偽署名。Noise (`pair.rs:198` `NoisePattern`, `pair.rs:770` `begin_handshake`) は鍵交換なしの状態機械 |
| **A7** | 中断耐性 (自動返金) | △ | ✗ | `deadman_at` (`ecash.rs:234`) + `refund_escrow` (`ecash.rs:824`) + `process_deadman` は実装済みだが未到達。さらに返金経路には既知の不整合あり (§1.8) |
| **A8** | ゼロコンフィグ | **○** | **✓** | `should_show_first_run` (`first_run.rs:729`) → `step_identity` (`first_run.rs:312`) で鍵生成まで自動。`rope` 一発で完走する |

### 演繹された結論

**製品成立の必要条件 A1-A7 は、7 つすべてが未達 (到達可能なものゼロ)。**
唯一機能しているのは補助公理 A8 (ゼロコンフィグ) のみ。

これは `SURPLUS_AND_GAPS.md` §1.x が帰納的に導いた結論
(「実 I/O が皆無」「EcashManager 全体が未到達」) と**独立に一致する**。
異なる 2 つの分析手法が同じ結論に達したことは、この現状認識の確度を高める。

**最も重い発見は A3**: A1/A2/A4-A7 は「型はあるが中身が空」(△) なのに対し、
**A3 だけは型すら存在しない (×)**。他の 6 公理は「配線すれば動く形」まで
設計されているが、推論実行だけは**設計にも着手されていない**。
`ExecutionPlan` は「計画を立てる」までで、それを**実行する**主体がいない。

## 3. 過剰 (Surplus) の第一原理的再評価

帰納的監査 (`SURPLUS_AND_GAPS.md` §2) は「呼び出し元ゼロか」で判断した。
ここでは **「どの公理に対応するか」** で問い直す。公理に対応しないコードは、
呼ばれていようがいまいが、製品成立には不要である。

| 対象 | 対応する公理 | 第一原理での評価 |
|---|---|---|
| `pair::CapabilityChallenge` 一式 (~300行) | **A2 に直接対応** | **保持が演繹的に正当化される**。帰納的監査は「ロードマップに記載があるから保持」と判断したが、より強い根拠がある — A2 (未知の他人との信頼確立) は製品成立の必要条件であり、TOFU だけでは A2 を満たせない。これは「予約 API」ではなく**必須能力の先行実装** |
| `ecash` の escrow/streaming 一式 | **A5 + A7 に直接対応** | 同上。未到達だが**製品成立に不可欠**。削除候補として検討する余地はない |
| `confidential` の attestation 一式 | **A6 に直接対応** | 同上 (ただし署名が偽である点は A6 を満たさない — 型ではなく中身の問題) |
| `session.rs` の `SessionManager`/`panic_stop` クラスター (10関数) | **A9 に直接対応** ⚠️**2026-08-08 訂正** | ~~当初「A1-A8 のどれにも対応しない、ローカルプロセス管理という別レイヤーの関心事」と評価し削除材料としたが、**これは公理集合に A9 が欠けていたための誤判定**~~。`panic_stop` (`session.rs:360-380`) は停止フラグを立て **`docker ps --filter name=rope-` で Rope のコンテナを列挙し `docker kill` する** — **貸し手が借り手のワークロードを緊急停止する機構**そのもの。A9 (貸し手の保護) に直接対応するため **削除候補から外す**。根拠: [`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §4h |
| `format_*` 6個・QR/TOFU 統計 7個 | **どれにも対応しない** | **観測可能性 (運用) の要求**であって製品成立の必要条件ではない、と位置づけが明確になる。「表示するか削除するか」は A1-A7 が満たされた後に判断すべき低優先事項 |

## 4. 不足 (Gap) の優先順位を演繹で導出

**基準: どの公理が欠けると製品が「一歩も動かない」か。**

```
A1 (発見) ─┬─→ A2 (信頼) ─→ A6 (秘匿) ─┐
           │                              ├─→ A3 (実行) ─→ A4 (検証) ─→ A5 (対価) ─→ A7 (中断耐性)
           └──────────────────────────────┘
```

- **A1 が最優先**: 発見できなければ A2 以降すべてが起動しない。依存グラフの根。
- **A3 が次点**: A1 が解決してピアに繋がっても、実行できなければ価値ゼロ。
  かつ **A3 だけが型すら無い (×)** ため、他より着手コストが大きい。
- **A4 は A3 に依存**: 実行がないものは検証しようがない。
- **A5/A7 は最も「完成に近い」**: 実装済みで、A1/A3 が動けば結線するだけ。

> **2026-08-08 追記 — 依存グラフに 2 辺を追加**
> ([`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §4b):
>
> - **`A5 → A2` (逆方向の依存)**: TraceRank (arXiv:2510.27554) は
>   **支払いそのものを推薦として扱い、支払者の評判で重み付ける**。Rope は
>   既に ecash を持つため、**A5 が結線されると A2 の信頼根拠が副産物として
>   手に入る**。当初 A5 を A2 の後段と位置づけたが、逆向きの依存も存在する。
>   ただし Cashu の bearer token は無記名であり、素朴な適用は A6 と衝突する。
> - **`A4 → A2`**: DARTIC (arXiv:2605.18146) は評判を**検証可能な実行結果**で
>   駆動する。評判の入力が検証結果である以上、**A4 の検証が effort gap
>   (§1 Hollow-LLM) を見逃せば評判システムごと汚染される**。
>   A2 の評判設計は A4 の検証強度に依存する。
>
> いずれも A2 実装の**着手前に読むべき設計入力**であり、後から接ぎ木すると
> アーキテクチャをやり直す種類の判断 (匿名性と評判の両立)。

> **2026-08-08 追記その2 — `A6 ⊥ A8` の構造的緊張**
> ([`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §4e):
>
> GPU-CC の実測 (arXiv:2606.23969) では **GPU 計算自体はほぼ無損失
> (BF16 matmul が非機密の 0.998 倍)** だが、**LLM サービング全体では
> 13-27% のスループット損失**が出る。原因は計算ではなく
> **機密 VM ↔ GPU のブリッジ**で、転送が直列化され
> **小さな転送ほど固定コストの割を食う**。H100 でも同傾向
> (オーバーヘッドはバッチ・シーケンスが大きいほど縮小、TTFT > ITL から
> ボトルネックは I/O と結論)。
>
> → **Rope の「60 秒で 1 ドル未満」= 小さく短いジョブは、
> オーバーヘッドが最大化する領域**。つまり **A6 (秘匿) と A8 (体験) は
> 構造的に緊張する**。これは W4 (TEE 訴求と消費者 GPU の矛盾) とは別の、
> 性能面での矛盾。両立にはモデル常駐・ジョブごとの転送最小化といった
> 設計が要り、**A3 実装時に織り込む必要がある** (後付けは困難)。

> **2026-08-08 追記その3 — A8 の隠れた前提「ウォームな貸し手」**
> ([`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §4f):
>
> cold start の実測は **4 フェーズで 40 秒超** (イメージ pull 4-8 分 /
> 70B 重み転送 40 秒超 / CUDA 初期化 10-30 秒)、cold/warm 間に
> **1000 倍のレイテンシ差**。→ **「60 秒」は cold start を含めた瞬間に破れる**。
> A8 が成立するのは**貸し手側でモデルが既にウォームな場合のみ** — これは
> 明文化されていなかった A8 の前提。デモモデルが 1B 級
> (`first_run.rs:186`) である既存設計は偶然この制約に整合しており、
> **小型モデルの常駐 (`RESEARCH_IMPROVEMENTS.md` #11) は「最適化」ではなく
> A8 の成立条件**。副次の問い: 常駐コスト (keep-warm は GPU 費用 2-3 倍) を
> 誰が払うか — A5 の経済設計に「ウォーム維持の対価」が要る可能性。
>
> 供給側の実在は査読付きで裏付け済み (ACM AIBC 2025 の消費者 GPU 実証、
> Petals 800+ ノード、BOINC 500 万台、本番稼働率 40-65%) —
> **リスクは供給ではなく A3/A2/A4 の未実装に集中している**。

> **2026-08-08 追記その4 — 🔴 `A6 ⊥ A9` (公理 A9 の追加に伴う)**
> ([`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §4h):
>
> **借り手のプライバシー (A6) を完全にするほど、貸し手は自分の機材で
> 何が生成されているか知り得なくなる。** 生成 AI の CSAM に関しては
> **モデルを提供する側も二次的責任を負いうる** (知りながら助長、または
> **緩和を怠った**場合)。STOP CSAM Act of 2025 成立、good-faith な検出・
> 報告には safe harbor が提案されるが過失・無謀は保護しない。
> → TEE で中身が見えないことは、貸し手にとって**盾 (知り得なかった) にも
> 刃 (緩和を怠った) にもなりうる**。
>
> W4 (A6 vs 消費者 GPU の能力) と `A6 ⊥ A8` (A6 vs 60 秒体験) に続く
> **A6 絡み 3 つ目の構造的緊張**であり、しかも**技術ではなく法務の領域**。
> 「どこまで秘匿するか」は技術選定ではなく**製品・法務判断**になる。
>
> 技術面の含意 (A3 着手時): 2026 年の実務コンセンサスは
> 「Docker/runc は AI 生成コードに不十分、gVisor/MicroVM 必須」、さらに
> 「**信頼できないワークロードでは GPU アクセラレーションを無効化すべき**」
> (GPU デバイスノード経由の脆弱性 + 同一 GPU 上の side channel)。
> **Rope の緩和要因**: `Workload::Inference` はプロンプトのみで任意コード実行
> ではないため攻撃面は桁違いに狭い。**ただし `Workload::Train { dataset_uri }`
> と RAG は借り手指定 URI を貸し手がフェッチする** → **Inference と Train/RAG を
> 同じ脅威モデルで扱ってはいけない**。

### 既存バックログとの照合

`docs/RESEARCH_IMPROVEMENTS.md` / `CLAUDE.md` の優先順位は
「実 P2P 結線 / 実 BDHKE / 検証エンジン」が並んで最高優先。演繹の結論と比較すると:

- **一致**: 実 P2P (= A1) が最優先である点。演繹が既存判断を独立に裏付けた。
- **ずれ**: 既存バックログは **BDHKE (A5 の暗号的正しさ) を最高優先の一つ**に
  置くが、演繹では **A5 は A1/A3 に依存する後段**。BDHKE を完璧にしても、
  発見も実行もできなければ製品は一歩も動かない。
- **最大のずれ**: 既存バックログは検証エンジン (A4) を最高優先に置くが、
  演繹では **A3 (実行) が A4 の前提**。「実推論エンジン自体が未実装」という
  ブロッカーは既に記録されているものの、**A3 を独立した最優先項目として
  立てていない**のが既存バックログの盲点。第一原理で見れば、
  **推論エンジン統合は「検証の前提条件」ではなく、それ自体が製品の中核能力**。

### 演繹が示す推奨順序

1. **A1 — 実ピア発見** (`P2P_IMPLEMENTATION_READINESS.md` の Step 1)
2. **A3 — 推論エンジン統合** ← **既存バックログで独立項目として弱かった箇所**。
   `RESEARCH_UPDATE_2026-07.md` §6 の比較 (llama-cpp-rs vs mistral.rs) が着手点
3. A2/A6 — 信頼確立・秘匿 (A1 が動いて初めて意味を持つ)
4. A4 — 検証 (A3 の後にしか成立しない)
5. A5/A7 — 対価・中断耐性 (実装済み、結線待ち)

## 5. 現時点で Rope が本当に提供できている価値

正直に言えば **一つだけ**: **A8 (ゼロコンフィグ)**。

`rope` を引数なしで実行すると、鍵生成・設定作成・状態機械の完走までが
質問ゼロで走りきる (`first_run.rs:312,729`)。これは実装されており、実際に動く。

README の 6 つの約束のうち、他の 5 つ (他人GPU・TEE プライバシー・
独自トークン不要・ジョブ中断耐性・1秒単位課金) は、いずれも A1-A7 の未達により
**現時点では提供されていない**。この事実は README 冒頭・`SECURITY.md`・
`ASSESSMENT.md` で既に開示済みであり、本書はそれを公理レベルで裏付ける。

## 6. 本書の使い方

- **新機能を提案する時**: 「どの公理に対応するか」を最初に問う。
  A1-A7 のどれにも対応しないなら、それは製品成立に不要な機能である
  (観測可能性・運用の要求かもしれないが、優先度は A1-A7 の後)。
- **既存コードの削除を検討する時**: 帰納的判断 (呼び出し元ゼロ) に加えて、
  演繹的判断 (どの公理に対応するか) を併用する。両方で不要なら削除の確度が高い。
- **優先順位に迷う時**: §4 の依存グラフに戻る。根に近い公理ほど優先。

## 7. A8 の解剖 — 唯一機能する公理は何を保証し、何を保証しないか

§2 で A8 (ゼロコンフィグ) だけが ○ と判定された。唯一機能している能力こそ、
「本当に公理を満たしているか」「どこまでか」を精査する価値がある。

### `first_run` の 8 ステップと公理の対応

| ステップ (file:line) | 演じる公理 | 実際に行うこと |
|---|---|---|
| `step_identity` (`first_run.rs:312`) | — (A8 固有) | **本物**。鍵生成・設定作成を質問ゼロで実行 |
| `step_discovery_start` (`first_run.rs:326`) | A1 | stage 遷移のみ。探索 I/O なし |
| `step_discovery_complete` (`first_run.rs:342`) | A1 | `pair.paired` を読んで VRAM 最大のピアを選ぶ (`first_run.rs:347-354`)。**発見ではなく既存状態の参照**。空ならローカルへフォールバック |
| `step_attest` (`first_run.rs:405`) | A6 | ピア有無で TEE 種別を決める。コード自身が「**暫定: ピア有無で TEE 種別を決定 (実運用は Bob 側 GPU 種別を取得)**」と明記 (`first_run.rs:410-411`) |
| `step_build_intent` (`first_run.rs:491`) | — | `Intent` を組み立てる。**本物** (型としては完全) |
| `step_demo_completed` (`first_run.rs:523`) | **A3** | 引数で渡された文字列を保存するだけ (`first_run.rs:529`)。**推論は行わない** — 呼び出し元 (`main.rs`) が `sample_haiku_response()` の固定文を渡す |
| `step_finale` (`first_run.rs:536`) | — | 完了画面の組み立て |
| `step_done` (`first_run.rs:546`) | — | 終端遷移 |

### 演繹される 2 つの事実

1. **A8 は真に満たされている。誇張ではない。** 質問ゼロで鍵生成から完走まで
   走りきる体験は実在し、A1-A7 の未達とは独立に成立する UX 特性。
   `step_identity`/`step_build_intent` は型としても実装としても本物。

2. **ただし A8 の "動く" が指すのは状態機械の完走であって、価値の提供ではない。**
   A1 (発見)・A6 (attest)・A3 (実行) を演じる 3 ステップは、いずれも
   対応する公理の *形* を持ちながら中身が空。README 冒頭の
   シミュレーション注記は、この構造を正確に反映している (誇大表示ではない)。

### 設計上の含意 — これは改善に直結する

`first_run` は **A1-A7 実装時の統合テストハーネスとして既に完成している**。
各ステップが対応する公理の配線先を持ち、`step_attest` に至っては
コード自身が「実運用では何に置き換えるか」をコメントで明示している。

これは `P2P_IMPLEMENTATION_READINESS.md` が「`pair.rs` の状態機械・公開 API
シグネチャは変更不要、内部実装のみ差し替え」と述べた点の、`first_run` 側での
対応物である。実装セッションへの含意:

- **エンドツーエンドの統合テストを新規設計する必要がない。**
  `rope` 無引数の実行が、そのまま A1→A6→A3 の統合テストとして機能する。
- 実 I/O を差し込む箇所が既に決まっているため、**実装コスト見積りは
  「状態機械の設計込み」ではなく「既存の穴を埋める」規模**。

## 8. A3 (実行) の最小充足条件 — 演繹による導出

§2 で A3 だけが「型すら無い (×)」と判明した。では **何を追加すれば
A3 が最小限満たされるか** を、Rope の設計制約の下で演繹する。

A3 の最小定義: **借り手のプロンプトが実際にモデルで処理され、結果が返る。**

### 必須要素 (これ無しに A3 は成立しない)

| 要素 | 現状 | 備考 |
|---|---|---|
| 推論エンジンへのバインディング | **不在** | **`mistral.rs` を推奨** — 2026-08 調査で Rope の設計制約と突き合わせ確定 (pure Rust / Candle 0.9.2 / CPU 単独で動作 = §8 の「初回は CPU で十分」が実際に成立)。`llama-cpp-2` は C++ FFI + API 不安定 (作者が semver 非準拠を明言) で依存最小主義と衝突。根拠: [`RESEARCH_UPDATE_2026-08.md`](RESEARCH_UPDATE_2026-08.md) §2 |
| モデル重みの取得手段 | 不在 | **ローカルパス指定で最小充足**。CID/P2P 配布 (`RESEARCH_IMPROVEMENTS.md` #11) は A3 の必要条件ではなく最適化 — A3 成立後の課題 |
| `ExecutionPlan` → 実行の配線点 | 不在 | `resolve` (`intent.rs:603`) が `ExecutionPlan` (`intent.rs:396-408`) を返して終わっている。`steps`/`selected_model_variant` は揃っているが、**それを受け取って実行する主体がいない** |

### A3 に必要と誤認されやすいが、演繹上は不要なもの

第一原理の価値は「必要」の判定だけでなく「不要」の切り分けにもある:

- **決定論的推論** — これは **A4 (検証) の要求であって A3 の要求ではない**。
  `RESEARCH_IMPROVEMENTS.md` #1 が「検証の前提」としているのは正しく、
  本書と矛盾しない。A3 は「実行できる」ことだけを要求する。
  A3 実装時に決定論性を後回しにしても A3 自体は満たせる。
- **GPU / CUDA** — CPU 推論でも A3 は成立する。「60 秒」は A8 の体験要求で
  あって A3 の成立条件ではない (遅くても実行できれば A3 は満たされる)。
- **TEE** — A6 の要求。非 TEE ピアでも A3 は成立する
  (秘匿されないだけで、実行はできる)。

この切り分けにより、**A3 の初回実装は「CPU・非決定論的・非TEE・ローカル
モデルパス」で十分**と演繹できる。最小構成が明確になることで着手障壁が下がる。

### 設計制約との衝突と、既存アーキテクチャに沿った解法

Rope の `core/` は「I/O なし pure state machine」が既存方針
(`ARCHITECTURE.md`)。一方、推論は本質的に I/O (モデルロード・GPU 呼出) である。

**解法は既存の前例に倣う**: `net/cashu_mint.rs` が `#[cfg(feature = "http")]`
(`cashu_mint.rs:34,64,70`) で実 I/O を分離し、`Cargo.toml` の
`default = []` / `http = [...]` (`Cargo.toml:71-72`) で opt-in にしている
パターンがそのまま適用できる。

→ **`net/inference.rs` + `inference` feature** が、既存アーキテクチャと
最も整合する配置。`core/intent.rs` は `ExecutionPlan` を返すまでを担い続け、
実行は `net/` 側が担う。この配置判断は実装セッションが最初に迷う箇所なので、
演繹の段階で決めておく価値がある。
